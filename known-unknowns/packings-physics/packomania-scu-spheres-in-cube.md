# Packomania: equal spheres in a cube (scu), beat a per-N record radius

⚪ **Packings and physics** · harvest (many cells or partial wins within reach) · tractability ★★★☆☆ · compute: laptop-hours · open as of 2026-10-28

## The problem

Packomania's 'spheres in a cube' table (scu) lists the best known radius r(N) of N equal spheres in the unit cube, complete for N = 1..1000 plus lattice rows up to N = 1024192 (1134 rows; since the 17-Oct-2026 reorganisation txt/radius.txt gives 12 decimals for 1058 rows and 30 for 76; per-N coordinates scu/txt/scu<N>.txt). Proven only for N <= 10 and a few more. The table is being revised right now: 04-Oct-2026 Specht posted 2022 Lai-Hao-Xiao-Glover candidates for ~60 values of N and wrote 'This table needs a revision!'; 05-Oct-2026 Yuan Gao (Harvard) set ~80 records in 202..576; 06-Oct and 08-Oct-2026 Lu Peng set ~185 records across 102..946; 17-Oct-2026 Lu Peng continued (N in 95..883), Vidit Patankar set records for 40 values of N from 101 to 1596, and the table was reorganized. Author file (2026-10-20): Lu Peng 321 rows, Goldberg (1971) 262, Cantrell 231, Specht 173, Vidit Patankar 40, Lai-Hao-Xiao-Glover 39, so hundreds of rows are still 1970s-2012 constructions. scu is NOT in the pending-requests list of 17-Oct-2026, and the 'many: 4666 candidates' bundle from Moki & Julio of 26-Sep-2026 matches their public release v2.2, which has no scu table (see pitfalls).

## What counts as a win

Success means N centers in R^3 for one N listed in https://packomania.com/scu/txt/radius.txt such that the FEASIBLE radius r* := min( min_{i<j} |c_i - c_j| / 2, 1/2 - max_i max(|x_i|,|y_i|,|z_i|) ) for the cube [-1/2, 1/2]^3, computed in mpmath at 50 digits with no tolerance, is STRICTLY GREATER (direction: max) than the live txt/radius.txt value (12 or 30 decimals depending on the row since 17-Oct-2026) for that N re-fetched immediately before claiming, by at least 1e-11, AND beats what the posted files already give with no new search: B(N) := max over listed N' >= N of r(N') by at least 1e-11 (deleting N' - N spheres from the posted scu<N'>.txt keeps its radius), and by at least 1e-9 the highest radius that the verifier's own local polishes, each run until it stops improving, under several trust-region schedules, reach from the posted scu<N>.txt and from the largest-N' posted file attaining B(N) (files that list their centres), AND the configuration is not isometric to the posted scu<N>.txt configuration (sorted distance multisets differ) and is not a trivial derivation of a posted packing: the posted scu<N>.txt, a posted scu<N'>.txt (N' > N) with N' - N spheres deleted, or the posted scu<N-1>.txt with one sphere dropped into a hole, each followed at most by a local relaxation, however much that gains (#264 and #265 were closed as such derivations, and the deletion-plus-relax siblings #236 and #237 were folded into the packing they came from; a polish gain is an errata note for the table keeper; the claim names any posted packing it started from, and an object seeded from a posted packing by real search, for example several spheres inserted and the packing relaxed, counts, with credit, when it clears all of these bars), AND N does not appear in a History-of-updates line on the live scu.html newer than the one the scout fetched (the table was rewritten on 04, 05, 06, 08 and 17 Oct 2026 from private communications outside the public queue, so a same-day re-fetch is mandatory). QUEUE RULE (Packomania, checked 2026-10-20): the N must NOT lie inside any range listed for this category on https://packomania.com/pending-requests.html re-fetched at verification time; a value that is already in Packomania's queue does not count as ours. The 26-Sep-2026 'Moki & Julio *many* 4666 candidates' bundle is category-unspecified and cannot be resolved; the verdict must state this caveat and the N must be re-checked against the live table once that bundle disappears from the pending list. Packomania coordinate files are CENTERED (container centre at the origin: circle/sphere radius 1, square side 1 in [-1/2,1/2]^2, cube edge 1 in [-1/2,1/2]^3). ## Partial wins

- **p1:** A certified improvement (same rule) for an N whose live author (txt/author.txt) is 'Michael Goldberg' or 'Hugo Pfoertner' or 'Dave Boll' (pre-2000 hand constructions), i.e. a row nobody has optimized by computer; counted as a record if it passes the criterion, else as a near-miss with r* within 1e-6.
- **p2:** A certified improvement to the sibling 'spheres in a sphere' table (ssp, last update 26-Sep-2024, 1156 rows, 12-decimal txt/radius.txt) using the same mpmath feasible-radius rule against https://packomania.com/ssp/txt/radius.txt (container radius 1), margin 1e-10 because that file has only 12 decimals, same queue rule for category ssp. A p2 claim must also clear the full criterion's other bars against the posted ssp files: the deletion bar B(N) (by 1e-10), the polish floor and the derivation rule. Count the centre rows first: the live ssp100.txt, ssp144.txt and ssp155.txt (fetched 2026-10-29, Last-Modified 12 Jul 2026) list only N-1 centres (the row for index N is empty) and those reproduce the header radius to about 1e-12, so where the posted file is incomplete the verdict must say 'posted coordinates incomplete' and the N is re-checked once a complete file is posted.
- **p3:** Reproduction milestone: re-derive from scu<N>.txt the table radius (12 or 30 decimals) for all N <= 1000 and report any N where the posted coordinates do NOT achieve the posted radius (a data-integrity finding, which Deeter-style audits have found in other tables).

## How a win is checked

Checker (about an hour; the polishes take most of it): curl https://packomania.com/scu/txt/radius.txt live; load the claimed N centers; mpmath mp.dps=50; r* = min(half minimum pairwise distance, 1/2 - max_i max(|x_i|,|y_i|,|z_i|)); assert r* - r_table >= 1e-11 and r* - B(N) >= 1e-11, B(N) = max over listed N' >= N of r(N'). Download scu/txt/scu<N>.txt, scu<N-1>.txt and every scu<N'>.txt (N' > N) whose row lies within 1e-5 of B(N) (or the coordinate archive), count their centre rows, recompute their r (each must reproduce its 12-decimal row to about 2e-12; parser sanity) and compare the claim's sorted distance multiset with scu<N>.txt's. Polish scu<N>.txt and the largest-N' file attaining B(N) from their posted coordinates with your own local optimizer (for example sequential LP on the near contacts with a trust region) under at least three schedules (largest step 1e-2, 1e-3 and 1e-4), each until it stops improving; report every polished radius and assert r* exceeds the highest by at least 1e-9 (in a run of equal rows the smaller files are deletions of a larger one: scu886.txt and scu887.txt lie inside scu888.txt, scu740.txt inside scu741.txt). Compare the claim with each downloaded file under the 48 symmetries of the cube and report the share of its centres that lie within 1e-3 of a posted centre: #264 and #265 (scu<N-1>.txt plus one sphere) kept all but the added one, #526 and #527 (scu734.txt and scu741.txt with spheres deleted, then relaxed) kept all of them, our polishes of five Patankar files kept 44 to 98 percent, and the merged N = 884 and 886 objects keep 9 and 27 percent of the posted scu884.txt and scu886.txt. Read the claim's stated starting point and treat a relaxed copy of a posted file as its derivation unless the claim documents real search beyond a relaxation. Re-fetch scu.html History of updates and pending-requests.html and apply the queue rule. Report r* to 25 digits and the contact graph.

## Ideas to start from

Starting points, not instructions. The best wins came from angles nobody listed.

- Read txt/author.txt live and attack only rows still attributed to Goldberg/Pfoertner/Boll/Schaer (hundreds of N in 100..1000): these are decades-old constructions and the Oct-2026 waves by Gao and Peng show large gains are still routine there.
- Lattice-cut plus relax: cut fcc/hcp/bcc and 'layered square' lattices by the cube at many orientations and offsets, pick the best N-subsets, then inflate with an event-driven (Lubachevsky-Stillinger) compression and polish the active contacts with mpmath Newton.
- Peng/Gao ran N = 102..946; try the complementary N they did not touch (check the History of updates lists) and the rows between record clusters.
- Monotonic basin-hopping with a smooth overlap penalty; perturbation = remove the 3-5 'loosest' spheres (txt/loose.txt gives rattler counts) and re-insert at the largest cavities found by a Delaunay-based hole search.
- Rows N = 385..395 (and other runs) share one identical radius with ref [24]: they are a larger packing with spheres removed, so any genuine optimization of the smaller N beats them.

## Traps

False wins others have fallen for. A claim that walks into one of these will not survive the skeptics.

- The table is being rewritten daily (04-08 Oct 2026). A value fetched by the scout at 04:20 can be beaten by Packomania's own update before the verifier runs; re-fetch radius.txt immediately before claiming.
- Cube convention: coordinates are centered (edge length 1, [-1/2, 1/2]^3); testing against [0,1]^3 produces false protrusion or false feasibility.
- Noise in the 30th decimal is not a record; the 1e-11 margin on the mpmath feasible radius is mandatory.
- The 'many' bundle (4666 candidates, Moki & Julio, 26-Sep-2026) matches their public release v2.2 (github.com/Hashirama1337s/moki-julio-circle-packing, commit 855d8f6838e9, 2026-09-25T22:41Z, '4,666 records in 15 tables', all 2-D: crt, ccq, cpd, cpt, crc_100 to crc_800, csc, csq, cxd); spheres in a cube enter that repo only at v2.3 (commit ea2a2e66d21c, 2026-09-26T01:29Z). Where a polish stops depends on the run: converged runs on scu101.txt ended between 0.1102407305 and 0.1102407490 (1.9e-8 apart; restarts from 1e-4 random kicks of a lower one reached the top), on scu459.txt 4.5e-9 apart and on scu747.txt 1.3e-6 apart. So no margin over the row or over one polish separates a polish from a new packing (1e-10 does not, nor does 1e-9): the criterion takes the highest of several polishes only as a floor and treats a relaxed copy of a posted file as a derivation however much it gains. A polish gain over a posted file is an errata note for the table keeper, not a record (#605).
